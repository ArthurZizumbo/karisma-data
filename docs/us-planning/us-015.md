## Las ocho ambigüedades del enunciado, resueltas antes de planear

No son objeciones. Son bifurcaciones que, sin resolver, producen dos implementaciones distintas
de la misma US.

**1. «Selector de perfil de demostración» admite dos mecanismos incompatibles.** O el selector
rellena usuario y contraseña y envía el formulario —y entonces la contraseña de demostración
tiene que viajar al navegador, es decir, estar en el repositorio o en una variable pública—, o el
selector **no usa contraseña alguna**. Se elige el segundo: `POST /api/auth/demo` con cuerpo
`{"rol": "..."}`, **registrado en la aplicación solo cuando `DEMO_LOGIN_ENABLED` es verdadero**.
Razones, en orden: (a) es la única lectura en la que la frase de la propia US —*«habilitado
únicamente en este prototipo»*— corresponde a algo verificable en el código y no a un rótulo;
(b) hace literal la promesa de §6.0 del plan de excelencia, *«recorrer los cuatro espacios de
trabajo sin credenciales»*; (c) deja la contraseña de demostración fuera del repositorio **por
construcción**, no por disciplina. El costo se dice sin adornos en §2.4.

**2. «401 con mensaje neutro "Credenciales incorrectas"» contra la interfaz bilingüe.** Si el
cliente pintara el `detail` del backend, la pantalla mostraría español a un usuario en inglés. Se
resuelve partiendo el mensaje en dos: el backend devuelve el literal exacto que la US exige en
`detail` —comprobable con `grep`— y además `codigo: "credenciales_invalidas"`; **el cliente nunca
muestra el `detail`**: renderiza su propia clave i18n a partir del estado 401. El literal del
backend queda para el registro y para quien lea la API por Swagger.

**3. ¿Quién crea `backend/app/core/auth.py`, US-015 o US-016?** Reparto concreto en §5.3: **lo
crea entero US-015**, `get_current_user` con `SecurityScopes` incluido, y **US-016 no lo edita**.
US-016 aplica `Security(get_current_user, scopes=[...])` en los routers de datos, redacta
`docs/security.md` y escribe `tests/backend/test_rbac.py`. Se planean en paralelo; **se
implementan en secuencia, US-015 primero**, porque US-016 lee lo que US-015 escribe.

**4. La pantalla `/acceso` tiene hoy pruebas que su reescritura rompe.** No se «ajustan» para que
pasen: se retira `/acceso` de las dos aserciones de andamiaje de `pantallas.spec.ts` —el párrafo
«Contendrá…» y el título igual a la rama de A3—, porque la pantalla dejó de ser un marcador de
posición. Es la aplicación literal de la regla NON-NEGOTIABLE: *un test que fija el marcado de una
pantalla que la siguiente US va a reescribir es deuda; se borra en el primer cambio real*.

**5. El `DATABASE_URL` que existe hoy no sirve para asyncpg.** La cadena es
`postgresql://usuario:clave@db:5432/karisma?sslmode=disable`, con la forma que dbmate exige. El
dialecto asyncpg de SQLAlchemy no acepta `sslmode` —es un parámetro de libpq, no de asyncpg— y el
esquema tiene que ser `postgresql+asyncpg://`. Si nadie traduce, la API arranca y **falla en el
primer login**, no antes. Se resuelve con una función pura `build_async_dsn()` en
`app/core/database.py`, probada sin base de datos (§6.1). **Una sola variable de entorno sigue
sirviendo a dbmate y a la API**, que es lo que `backend/.env.example` promete.

**6. ¿Formulario o JSON en `/api/auth/token`?** Se elige el **flujo estándar de contraseña de
OAuth2**: `OAuth2PasswordRequestForm`, `application/x-www-form-urlencoded`, campos `username` y
`password`. Motivo: es el que `OAuth2PasswordBearer` documenta en `/docs`, el que hace funcionar
el botón *Authorize* de Swagger —la herramienta con la que se prueba a mano cada endpoint de
US-016— y el que las tools del agente esperarán en E3. La conversión de JSON a formulario la hace
la ruta de Nitro, que es un detalle de una función y no del contrato.

**7. ¿Cuál es el destino después de entrar?** §6.0 del plan de excelencia dice que el patrón que
demuestra la pantalla es *«espacios de trabajo por rol: el destino tras entrar cambia según el
perfil»*. Se implementa ya, con rutas que **existen** hoy: operativo → `/inicio`, analista →
`/exploracion`, directivo → `/exploracion/tableros`, admin → `/administracion`. Una única función
`destinoPorRol()` concentra la decisión, para que US-027 cambie una función y no cinco
componentes.

**8. El proxy de US-001 prometió por comentario una limitación de intentos que esta US no
entrega.** Limitar por IP no está en ningún criterio de aceptación de US-015, y añadirlo es
exactamente el desbordamiento de alcance que R11 prohíbe. Decisión: **no se implementa**, el
comentario de `[...].ts` se corrige para no prometer, y se abre `docs/us-backlog/04-…` con el
motivo. Un comentario que promete lo que nadie hará es peor que la ausencia del comentario.

## 2. Arquitectura de la solución y flujo de capas

### 2.1 El recorrido completo de un login, con sus cuatro fronteras

```
navegador                Nitro (frontend/server)              FastAPI (backend/app)          PostgreSQL
    |                             |                                     |                        |
    |  POST /api/auth/token       |                                     |                        |
    |  JSON {usuario, contrasena} |                                     |                        |
    |---------------------------->| api/auth/token.post.ts              |                        |
    |                             |  form-urlencoded, sin cookie        |                        |
    |                             |------------------------------------>| api/auth.py            |
    |                             |                                     |  services/auth_service |
    |                             |                                     |  core/security.verify->| app_user
    |                             |                                     |<-----------------------|
    |                             |<--- 200 {access_token, token_type}  |                        |
    |                             |                                     |                        |
    |                             |  GET /api/auth/me + Authorization   |                        |
    |                             |------------------------------------>| core/auth.get_current_user
    |                             |<--- 200 UserOut                     |                        |
    |                             |                                     |                        |
    |<-- Set-Cookie: karisma_sesion=<jwt>; HttpOnly; SameSite=Strict; Path=/; Max-Age=1800       |
    |    cuerpo: {usuario, nombre, rol}   SIN access_token                                        |
    |                             |                                     |                        |
    |  GET /api/auth/me           |  [...].ts inyecta Authorization     |                        |
    |---------------------------->|  desde la cookie ------------------>| 200 UserOut            |
```

Las cuatro fronteras, en el orden en que un fallo las atraviesa:

1. **navegador ↔ Nitro** — cruzan JSON y una cookie que el JavaScript del cliente no puede leer.
   El token **no** cruza esta frontera en ninguna dirección.
2. **Nitro ↔ FastAPI** — cruzan `application/x-www-form-urlencoded` y `Authorization: Bearer`.
   Nunca cruza una cookie: el proxy la vacía (§2.3).
3. **router ↔ servicio** — `api/auth.py` no verifica contraseñas ni construye tokens; delega en
   `services/auth_service.py`.
4. **servicio ↔ base** — `services/user_service.py` es la única capa que habla SQL, detrás de un
   `Protocol` que las pruebas sustituyen sin levantar PostgreSQL.

### 2.2 Por qué el módulo de auth se parte en dos archivos

La US pide `backend/app/core/auth.py`. Ese archivo necesita leer el usuario de la base para
comprobar `disabled`, y el servicio de autenticación necesita cifrar y firmar. Escrito como un
único módulo, `core/auth.py` importaría `services/user_service.py` y `services/auth_service.py`
importaría `core/auth.py`: ciclo.

Se parte por responsabilidad, no por tamaño:

| Archivo | Contiene | Depende de |
|---|---|---|
| `core/security.py` | Primitivas puras: `password_hash`, `hash_password`, `verify_password`, `create_access_token`, `decode_access_token`, `ALGORITHM`, `ACCESS_TOKEN_EXPIRE_MINUTES` | Solo `config` y las librerías |

### 2.3 La cookie: quién la pone, quién la lee, quién la borra

| Momento | Actor | Qué hace |
|---|---|---|
| Login correcto | `server/api/auth/token.post.ts` | `setCookie(event, 'karisma_sesion', token, opcionesDeCookie(event))` |
| Login de demostración | `server/api/auth/demo.post.ts` | Lo mismo, con el token que devuelve `/api/auth/demo` |
| Cualquier `/api/**` posterior | `server/api/[...].ts` | Lee la cookie y **reescribe** `authorization: Bearer <token>`; sin cookie, `authorization: ''` |
| Salida | `server/api/auth/logout.post.ts` | `deleteCookie(...)` y 204. **No llama al backend**: el JWT es sin estado y no hay lista de revocación — eso es lo que significa «sin refresh token» |
| Expiración | El navegador | `Max-Age` = 1800 = la vida del token. La cookie muere cuando muere el token; no queda una cookie viva apuntando a un token muerto |

Las opciones viven en `server/utils/sesion.ts` y las comparten las tres rutas (regla DRY):
`httpOnly: true`, **`sameSite: 'strict'`**, `path: '/'`, `maxAge: 1800`,
`secure: getRequestURL(event).protocol === 'https:'`.

**Por qué `secure` se deriva del protocolo y no de `import.meta.dev`.** Bajo Docker Compose el
contenedor `web` corre el *build* de producción sobre `http://localhost:3000`: `import.meta.dev`
es falso y una cookie `Secure` sobre http **no se guarda**. El login funcionaría en `pnpm dev` y
fallaría en `make dev`, que es el entorno donde se graban las capturas. Derivarlo del protocolo
acierta en los tres entornos sin añadir una bandera.

**Por qué `SameSite=Strict` y no `Lax` — el repositorio gana sobre la preferencia.** La primera
versión de esta planeación eligió `Lax`, para que el evaluador que abre el enlace del PDF cayera
en `/inicio` ya con sesión. **`docs/us-handoff/us-001.md` QA-M2 ya había decidido otra cosa, y lo
había escrito como criterio de aceptación de esta US**: cookie `SameSite=Strict; Secure; HttpOnly`
**más** rechazo en el proxy de los métodos no seguros cuando `Origin`/`Sec-Fetch-Site` no sea del
propio sitio. Manda la decisión escrita. El costo real es pequeño y conocido: con `Strict`, una
navegación entrante desde otro sitio llega sin cookie y el visitante aterriza en `/acceso`, donde
el selector de demostración lo hace entrar en un clic. A cambio, el `<form method="POST">` alojado
en cualquier parte que QA-M2 describe deja de poder actuar con la sesión de la víctima.

### 2.3.b La otra mitad de QA-M2: verificación de origen en el proxy

`SameSite=Strict` es la defensa del navegador. QA-M2 exige además una del servidor, porque un
navegador antiguo o una extensión pueden no aplicarla. En `server/api/[...].ts`, antes de
reenviar:

```
si el método no es GET/HEAD/OPTIONS:
    si Sec-Fetch-Site existe y no es 'same-origin' -> 403
    si no existe y Origin existe y su origen != el de la solicitud -> 403
    si no existe ninguno de los dos -> se deja pasar (cliente no navegador: curl, las tools del agente)
```

Son unas quince líneas y cubren el hueco exacto que la auditoría de US-001 dejó abierto **a
propósito, esperando esta US**. No se inventa un token anti-CSRF: con la cookie `Strict` y la
verificación de origen, un token sincronizador añadiría estado a un diseño que no lo tiene.

### 2.4 El acceso de demostración, y lo que cuesta

`POST /api/auth/demo` con `{"rol": "operativo|analista|directivo|admin"}` devuelve un token
idéntico al de un login normal —mismos claims, misma expiración, mismos scopes— para el usuario
canónico de ese rol. Tres candados:

1. **Registro condicional.** `create_app()` monta el router solo cuando
   `settings.demo_login_enabled` es verdadero. Apagado, la ruta **no existe**: 404 y ninguna
   entrada en `/openapi.json`. No es un 403, que confirmaría que la puerta está ahí.
2. **Apagada por omisión.** `demo_login_enabled: bool = False`. Un entorno que olvide la variable
   queda cerrado. Encenderla es un acto deliberado y en Cloud Run se escribe en el
   `--set-env-vars` del despliegue.
3. **Rotulada en la respuesta y en pantalla.** La respuesta del endpoint lleva
   `modo: "demostracion"` (§4.7) y el selector lleva su etiqueta, en los dos locales, junto a los
   cuatro botones. Es el mismo compromiso de honestidad que la franja de alcance de US-001.

Y el costo, dicho sin adornos: **es una puerta sin credencial**. Con la bandera encendida,
cualquiera que alcance la URL entra, incluso como administrador. Es aceptable en un prototipo
evaluado, con datos sintéticos y un aviso permanente de que no está conectado a ningún sistema
real, y **deja de serlo el día que haya un dato real**. Queda escrito en `docs/security.md`
(US-016) y en el handoff.

### 2.4.b `/api/auth/demo` es una ruta pública por diseño *(corrección 11-ago-2026)*

La auditoría cruzada del 11-ago encontró un defecto **bloqueante en la frontera con US-016**: su
guardia `assert_scope_coverage` aborta `create_app()` cuando una `APIRoute` bajo `/api` no declara
scopes ni figura en `PUBLIC_ROUTES`, y esa lista blanca tenía **un solo elemento**,
`POST /api/auth/token`. Con `DEMO_LOGIN_ENABLED=true` —el estado en el que se graban las capturas
de A4 y en el que el evaluador entra sin credenciales— la aplicación **no arrancaba**.
**Ya está corregido del lado de US-016**: `RouteKey("POST", "/api/auth/demo")` entra en
`PUBLIC_ROUTES`. Lo que sigue es la contrapartida que esta US se obliga a cumplir para que esa
entrada sea defendible.

| Propiedad | Compromiso de US-015 | Dónde se verifica |
|---|---|---|
| **Pública por diseño** | `POST /api/auth/demo` emite un token **sin credenciales**: exigirle un token sería exigir un token para emitir un token, igual que `POST /api/auth/token`. No lleva `Security(get_current_user, ...)` ni lo llevará | §4.7; `PUBLIC_ROUTES` de US-016 |
| **Existencia condicionada** | La ruta existe **si y solo si** `DEMO_LOGIN_ENABLED` es verdadero. No es un endpoint permanente con un `if` dentro: es un router que no se monta | CA-10, `test_auth_demo.py::test_con_bandera_apagada_la_ruta_no_existe` |
| **Registrada en la lista blanca de US-016** | La entrada la escribe US-016 en `backend/app/core/permissions.py`. US-015 **no toca ese archivo**; lo que hace es no cambiar el método ni el path sin avisar a US-016 el mismo día | §5.3, fila nueva |
| **Escalada de privilegio imposible** | `demo_login` **lee la fila del usuario canónico en `app_user`** y emite el token con el `role` de esa fila. El rol del cuerpo solo **selecciona** al usuario canónico; no se copia al claim. El token de demostración lleva **exactamente los mismos scopes** que ese usuario tendría entrando con su contraseña, **nunca más**, y hereda `disabled`: un usuario canónico desactivado da 401, no un token | `test_auth_demo.py::test_el_scope_sale_de_la_fila_y_no_del_cuerpo` |
| **Rotulada** | La respuesta lleva `modo: "demostracion"` y el `summary` de OpenAPI lo dice; la interfaz lo rotula antes de entrar con `acceso.demostracion.etiqueta`, en `es` y en `en` | CA-9, §4.7, §4.11 |
| **Se apaga en el despliegue** | El día que el prototipo deje de ser una demostración evaluada —cualquier dato que no sea sintético— la bandera se apaga en el `--set-env-vars` de Cloud Run. Es el gate de US-003 y la fila 5 de la deuda del handoff | §7, `docs/security.md` (US-016) |
| **Apagarla no puede romper el arranque** | Con la bandera apagada la ruta no existe y la entrada de `PUBLIC_ROUTES` queda **sin ruta viva**, que en el diseño de US-016 no es violación (lo contrario sí: ruta viva sin entrada). Los dos estados de la bandera construyen la aplicación | CA-19; la prueba que cruza guardia **y** bandera es de **US-016 ventana B** |

Dicho en una línea, porque es lo que otro plan necesita saber: **la ruta es pública, opcional y
acotada por la fila del usuario; su presencia o su ausencia son igual de válidas para la guardia.**

### 2.5 De dónde salen los hashes sin que la contraseña entre al repositorio

```
KARISMA_DEMO_PASSWORD  (entorno del proceso, jamás un literal)
            |
            v
scripts/generar_hashes_demo.py --sql        -> 7 filas INSERT con $argon2id$... por salida estándar
                               --verificar  -> lee la migración, verify() sobre las 7 filas, exit 0/1
            |
            v  (pegado una sola vez, a mano)
db/migrations/<ts>_create_app_user.sql       <- solo hashes; nunca la contraseña
```

El generador **no escribe ningún archivo**: imprime. Es deliberado. Un generador que reescribe la
migración invita a regenerarla, y una migración ya aplicada no se edita nunca (regla de
`db/AGENTS.md`). Argon2 usa sal aleatoria: dos corridas dan hashes distintos y ninguna prueba
puede fijar su valor — por eso las pruebas fijan **formato y correspondencia**, no contenido.

**Respuesta a la pregunta de dónde puede estar la contraseña en claro:** en **un solo sitio**,
`backend/.env.local`, que `.gitignore` excluye y que nunca se commitea. No está en el SQL, ni en
el frontend, ni en `.env.example` —que la declara con valor vacío, igual que las tres
obligatorias—, ni en el manual de pruebas, que la nombra por variable. Es aceptable porque ese
archivo no sale de la máquina del desarrollador y porque **el evaluador no la necesita**: entra
por el selector de demostración. Si el equipo quisiera compartirla, el sitio correcto es el canal
privado del equipo; y aun compartida, lo que protege al prototipo no es el secreto de esa
contraseña sino que todos los datos son sintéticos.

**no se corrige en esta US** (deuda 2 del handoff, US-017); lo que esta US garantiza es que esa
palabra **no cruza ninguna frontera de red**: no está en el token, ni en la migración, ni en la
respuesta de `/api/auth/me`, y `esRolUsuario` la rechaza (§6.2).

**C-2. El claim exacto del JWT donde viajan.** Token HS256 firmado con `JWT_SECRET_KEY`, sin
cifrar, cuatro claims y ninguno más:

| Claim | Tipo | Contenido | Regla |
|---|---|---|---|
| `sub` | `str` | El `username` de la fila de `app_user` (por ejemplo `lmendez`) | Es el identificador de sesión; nunca el correo ni el UUID |
| **`scope`** | `str` | **Cadena delimitada por espacios que hoy contiene exactamente un literal de C-1** | Convención de OAuth 2.0, adoptada de la ambigüedad 3 de US-016. `parse_scope_claim` de US-016 la parte por espacios y descarta lo desconocido. Un token con dos roles funcionaría sin cambiar una línea |
| `iat` | `int` | Emisión, en segundos epoch | — |
| `exp` | `int` | `iat + 1800` **exactamente** | Constante de módulo, no configuración (§4.1) |

`decode_access_token` valida con `algorithms=["HS256"]` y
`options={"require": ["exp", "sub", "scope"]}`: un token sin `scope` es 401, no un token con cero
permisos. **El claim se llama `scope`, en singular.** No es `scopes`, ni `role`, ni `roles`; el
campo de la tabla y del contrato de respuesta sí se llama `role`, y son cosas distintas a propósito:
uno es la fila, el otro es la reclamación firmada.

**C-3. Los siete usuarios sembrados, con su identificador exacto.** Los emite la migración

**Por qué `role: str` en la tabla y `role: Scope` en el contrato.** Si el modelo con `table=True`
declarara el campo como `Scope`, SQLAlchemy lo mapearía a su tipo `Enum`, que asume un tipo

la API valida el vocabulario. La coherencia entre ambos la fija una prueba que compara los valores
de `Scope` con el `CHECK` de la migración (§6.1), y los dos con la tabla C-1 de §4.0.

## 8. Migración: SQL real y su reversa

Archivo: `db/migrations/<timestamp>_create_app_user.sql`, creado con
`make db-new SLUG=create_app_user`. El sello de tiempo lo pone dbmate; no se escribe a mano.

```sql
-- Segunda migracion del proyecto: la tabla de usuarios del portal y sus siete
-- perfiles sembrados.
--
-- Las contrasenas van PREHASHEADAS con argon2id (pwdlib). El SQL no contiene, ni
-- puede contener, la contrasena en claro: los hashes se generan fuera con
--     KARISMA_DEMO_PASSWORD=... poetry -P backend run python scripts/generar_hashes_demo.py --sql
-- y se pegan aqui una sola vez. La correspondencia entre los siete hashes y la
-- contrasena documentada se comprueba con el modo --verificar del mismo script.
--
-- gen_random_uuid() es funcion del nucleo desde PostgreSQL 13: no hace falta
-- pgcrypto y por eso esta migracion no habilita ninguna extension.
--
-- Los siete usuarios son las personas de A1 agrupadas en los cuatro roles de
-- control de acceso: un administrador y dos por cada perfil de dato.

-- migrate:up
CREATE TABLE app_user (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    username        TEXT NOT NULL UNIQUE,
    email           TEXT NOT NULL UNIQUE,
    full_name       TEXT NOT NULL,
    hashed_password TEXT NOT NULL,
    role            TEXT NOT NULL
                    CHECK (role IN ('operativo', 'analista', 'directivo', 'admin')),
    disabled        BOOLEAN NOT NULL DEFAULT false,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

COMMENT ON TABLE  app_user                 IS 'Usuarios del portal. Baja logica con disabled, nunca DELETE.';
COMMENT ON COLUMN app_user.hashed_password IS 'argon2id via pwdlib. Jamas texto plano, jamas serializado en una respuesta.';
COMMENT ON COLUMN app_user.role            IS 'Scope del JWT: operativo | analista | directivo | admin.';

INSERT INTO app_user (username, email, full_name, hashed_password, role) VALUES
    ('movalle',    'movalle@karisma.demo',    'Mariana Ovalle',   '$argon2id$<hash 1>', 'admin'),
    ('lmendez',    'lmendez@karisma.demo',    'Laura Mendez',     '$argon2id$<hash 2>', 'operativo'),
    ('eruiz',      'eruiz@karisma.demo',      'Elena Ruiz',       '$argon2id$<hash 3>', 'operativo'),
    ('dhernandez', 'dhernandez@karisma.demo', 'Diego Hernandez',  '$argon2id$<hash 4>', 'analista'),
    ('jmendieta',  'jmendieta@karisma.demo',  'Jorge Mendieta',   '$argon2id$<hash 5>', 'analista'),
    ('acastaneda', 'acastaneda@karisma.demo', 'Arturo Castaneda', '$argon2id$<hash 6>', 'directivo'),
    ('rvaldez',    'rvaldez@karisma.demo',    'Roberto Valdez',   '$argon2id$<hash 7>', 'directivo');

-- migrate:down
DROP TABLE IF EXISTS app_user;
```

`<hash N>` es el marcador de posición de esta planeación: en el archivo real va la cadena completa
`$argon2id$v=19$m=...,t=...,p=...$<sal>$<digest>` que imprime el generador. **Ningún hash de este
documento es un hash real**, y ninguno se puede fijar en una prueba: Argon2 sala al azar.

**Sobre los nombres sin acentos en el SQL.** `Laura Mendez`, `Arturo Castaneda`, `Diego Hernandez`
van sin diacríticos en la migración a propósito: el volcado de `schema.sql` lo produce un
`pg_dump` 18.4 contra un servidor 15.18 (documentado en `docker-compose.yml`) y no se gana nada
metiendo UTF-8 no ASCII en un archivo que se compara byte a byte en CI. El nombre con acentos es
un dato de presentación y llegará con el CRUD de US-018 si hace falta; el `full_name` sembrado
sirve para saludar en pantalla, no para imprimir un documento oficial.

### 8.1 Reversibilidad, probada y no supuesta

```bash
make db-up                     # aplica create_app_user y regenera db/schema.sql
git diff --stat db/schema.sql  # debe mostrar la tabla app_user y su version en schema_migrations
make db-rollback               # DROP TABLE app_user
make db-up                     # vuelve a aplicarla
git diff --exit-code db/schema.sql   # sale 0: el ciclo es idempotente
```

La reversa borra la tabla entera, usuarios sembrados incluidos. Es correcto: son datos de la
propia migración, no datos de un usuario del portal. La regla de baja lógica de `db/AGENTS.md`
aplica a las **operaciones del API** —US-018 desactiva, nunca borra—, no a la reversa de la
migración que creó las filas.

- **Sin índice adicional.** La única consulta de esta US es por `username`, y el `UNIQUE` ya crea
  su índice. Un índice por `role` sin consulta que lo use es peso muerto que además hay que revertir.
- **Sin `updated_at`.** Nada actualiza filas todavía. Lo añadirá US-018, que es quien introduce la

- **Sin `last_login_at`.** Requiere un `UPDATE` por login: escritura en el camino caliente de la

- **Sin tocar `enable_pgvector_extension`.** Migración ya aplicada; no se edita jamás.

| Apartado de la rúbrica A4 | Peso | Qué aporta esta US |
|---|---|---|
| **3. Prototipos de alta fidelidad** — 10 puntos por prototipo, tope 50 | 50 % · 12.50 pts | **La pantalla 0, Acceso**, es uno de los siete prototipos entregados (§6.0 del plan de excelencia). Esta US la convierte de marcador de posición en pantalla operable |
| 4. Guía de estilos | 45 % · 11.25 pts | Aporta materia prima, no secciones: los **cinco estados** de `/acceso` y los estados de campo —normal, foco, error, deshabilitado— que la lámina de campos de US-UX-09 retrata. La sección la escribe US-UX-09 |

Los cuatro requisitos que la rúbrica pone a un prototipo de alta fidelidad, contrastados uno a uno
con lo que entrega esta US:

| Requisito de la rúbrica | Cómo lo cumple |
|---|---|
| *Representar fielmente el producto final* | El login es real: PyJWT, Argon2, PostgreSQL. No hay simulación de sesión |
| *Permitir probar interacciones y funcionalidades* | Cinco estados navegables, error en línea, mostrar/ocultar contraseña, y un destino distinto por rol |
| *Recoger comentarios sobre la estética* | La pantalla usa los tokens `@theme` de US-UX-09; se ve como el sistema, no como una maqueta suelta |
| *Hacer entender el producto a las personas interesadas* | El selector de demostración deja al evaluador recorrer los cuatro espacios de trabajo **sin credenciales**, que es la diferencia entre un prototipo que se explica y uno que se usa |

Y el elemento que también responde a la banda «Completo» de la rúbrica sin ser un requisito
explícito: la **etiqueta de honestidad** del selector. Un prototipo que declara qué parte de sí
mismo existe solo para la evaluación se lee como producto pensado, no como demostración maquillada.

## 12. Correcciones de la auditoría cruzada del 11-ago-2026

Los cuatro planes de Fase 2 de esta semana (US-006, US-008, US-015 y US-016) se escribieron **en paralelo por
agentes que no se vieron entre sí**. Una auditoría adversarial posterior —cinco lentes de revisión y una
refutación independiente por hallazgo— levantó 50 defectos candidatos y confirmó 13. Tres tocan a esta US.

| # | Gravedad | Qué decía la planeación del 10-ago | Qué dice ahora | Secciones tocadas |
|---|---|---|---|---|
| 1 | **BLOQUEANTE** | `POST /api/auth/demo` se montaba bajo el prefijo `/api/auth` sin más comentario. US-016 instala una guardia que aborta `create_app()` si una ruta bajo `/api` no declara *scopes* ni figura en su lista blanca, y esa lista tenía **un solo elemento**. Con `DEMO_LOGIN_ENABLED=true` —el valor que la propia plantilla de entorno deja puesto— **la aplicación no arrancaba**: ni `make dev` ni el contenedor de Cloud Run | La ruta es **pública por diseño y está declarada como tal**. US-016 la añadió a `PUBLIC_ROUTES`; esta US se obliga a la contrapartida: emite exactamente los *scopes* que la fila de `app_user` concede y ni uno más, se rotula como acceso de demostración en la respuesta y en la interfaz, y **apagar la bandera no puede romper el arranque**. CA-19 lo fija como criterio verificable con la bandera en los dos estados | Cabecera · CA-19 · §2.4.b · §4.7 · §5.3 |
| 2 | ALTO | Los nombres de *scope*, el *claim* del JWT y los siete usuarios sembrados estaban repartidos por el documento | Reunidos en una tabla única marcada como **contrato**: otros dos planes leen de ahí. US-016 construye su matriz de permisos sobre esos cuatro literales y US-008 declara el *scope* de su endpoint contra la misma matriz | §3 (tabla de usuarios) · §4 (firmas del JWT) |
| 3 | ALTO | La verificación manual citaba un usuario que esta US no siembra | Todo `curl` golpea una ruta que existe al cerrar **esta** US, con un usuario que **esta** US siembra (`lmendez`, no `laura.mendez`) y con la forma de cuerpo que **este** endpoint acepta. Lo que no se puede ejecutar al cierre se declara diferido y se dice a qué US | §6.5 |

**La lección, que vale para el resto de la semana**: planear varias US en paralelo con agentes ciegos entre sí
es rápido, pero produce colisiones en tres sitios predecibles —archivos generados que un segundo plan quiere
editar a mano, directorios de pruebas compartidos, y listas blancas de seguridad que no ven los endpoints que
otro plan inventa—. Auditar las fronteras después de cada abanico de planeación deja de ser opcional.
