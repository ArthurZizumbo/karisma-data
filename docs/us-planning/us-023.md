## Ambigüedades del enunciado, resueltas antes de planear

**1. `portal-sse-streaming` y el Contrato SSE v1 se contradicen en los nombres de campo.** La skill fija
`{id, tool, args_resumen, status: "announced"|"running"|"done"|"error"}` y `done` con `{ttft_ms, tool_calls_count}`;
el contrato congelado fija `{id, estado, herramienta, etiqueta, transcurrido_ms, resultado, fuente, paso}` y
`done` con `{motivo, tokens_emitidos, duracion_ms}`. **Manda el Contrato SSE v1**, porque es el que firmaron
las tres US del chat y romperlo obliga a reescribir el cliente de US-024 y US-028. La skill se cita como
origen de las **reglas** (anuncio antes del dato, `aclose()`, cleanup probado), no de los **nombres**. Queda
escrito en el handoff para que la próxima lectura de la skill no lo reabra.

**2. ¿Qué scope exige `/api/chat`?** La matriz de US-016 dice «consultas puntuales = operativo+». El chat es
una consulta puntual con otra piel. **Se exige `scopes=["operativo"]`**, no `scopes=[]`: si mañana entra un rol
de solo lectura por debajo de `operativo`, el catálogo sigue abierto y el asistente no. Consecuencia inmediata:
los tres perfiles de consulta del enunciado (operativo, analista, directivo) pasan y solo un token vacío o
caducado se queda fuera.

**3. `EventSource` o `fetch` con `ReadableStream`.** `EventSource` es la API canónica de SSE pero **no admite
POST, no admite cabeceras y no admite `AbortController`**, y esta US se juega entera en la cancelación.
**Se usa `fetch` + `response.body.getReader()` + `AbortController`**, parseando el framing `event:`/`data:` a
mano en el composable. La sesión viaja en la cookie `httpOnly` que ya emite US-015, así que no hace falta
cabecera `Authorization` desde el navegador: el proxy Nitro la traduce. Se paga un parser de ~40 líneas y se
compra la única cancelación que el criterio de aceptación acepta.

**4. ¿Se instrumenta TTFT ahora?** La skill lo pide como atributo de span OTel con objetivo p50 < 700 ms.
**Decisión: no se instrumenta OTel en S4, y sí se calcula el número.** Razón: con `ProveedorGuionizado` el TTFT
mide el `asyncio.sleep()` del propio guion, es decir, **mide una constante que nosotros elegimos**; publicarlo
como métrica de rendimiento sería una cifra honesta sobre un sistema que no existe todavía, exactamente lo que
la regla anti-alucinación prohíbe hacia el usuario. Lo que sí se hace, porque cuesta cinco líneas y evita una
refactorización el sábado: el servicio mide `primer_token_ms` y lo emite **en el log estructurado de cierre**,
nunca en el evento `done` ni en la UI. El día que entre `ProveedorGemini`, ese número pasa a ser un atributo de
span sin tocar el contrato del cliente. OTel completo es E5.

**5. ¿Dónde vive el guion determinista?** Podía ir en un `.json` de datos o en Python. **Va en Python, dentro de
`backend/app/services/proveedores/guionizado.py`**, como estructuras `Final` tipadas. Razón: el guion debe ser
**validable por mypy y por la prueba anti-alucinación**; un JSON obliga a escribir un validador de esquema que
no aporta nada porque nadie edita el guion desde fuera del repositorio. Además el contrato congeló los dos
archivos de `proveedores/` y añadir un tercero rompería el write-set disjunto.

**6. ¿El evento `done` se emite también cuando el cliente ya colgó?** El contrato dice «`done` siempre cierra el
stream, exactamente una vez, incluso al cancelar». Con el socket cerrado ese `yield` **no llega a nadie**.
**Se emite igualmente**, por dos razones operativas: (a) el generador tiene un único camino de salida, lo que
hace que el contador de streams activos se cierre siempre en el mismo sitio; (b) las pruebas de unidad
consumen el generador **sin socket** y necesitan ver el `done(cancelado)` para poder afirmar algo. Que el byte
se pierda en la red es irrelevante; que el invariante se rompa, no.

**7. ¿Qué es exactamente «no deja tareas colgadas»?** `asyncio.all_tasks()` a secas es una prueba que casi
nunca falla: en la suite de pytest hay tareas del propio bucle y el conteo es ruidoso. **Se sustituye por un
registro explícito**: `chat_stream` mantiene `_STREAMS_ACTIVOS: dict[str, float]` (id → `monotonic()` de inicio),
da de alta en el primer `yield` y da de baja **en el `finally`**. La prueba afirma `_STREAMS_ACTIVOS == {}` tras
cancelar. Defecto que la haría fallar: quitar el `finally` o sustituirlo por un `except` que no cubra
`CancelledError` (§6, prueba B-11). Se **añade** el conteo de `asyncio.all_tasks()` como aserción secundaria con
delta relativo (antes vs. después), no absoluto.

**8. ¿La franja de honestidad de demo es texto o componente?** El contrato la fija como «franja permanente
sobre la conversación» con clave `chat.demo.scriptedNotice`. **Se implementa dentro de `asistente.vue`**, no
como componente nuevo: crear `components/chat/AvisoDemo.vue` invadiría el directorio que US-024 y US-028
comparten y añadiría un archivo no previsto en el contrato de propiedad. Es markup de cinco líneas.

### 1.1 La captura de la cancelación — comando exacto y dónde vive

El criterio dice literalmente «La prueba se documenta con una captura del registro del servidor». No se acepta
una captura de pantalla del navegador: prueba que la UI cambió, no que el servidor se enteró.

```bash
# 1) Levanta el backend con log JSON en un puerto efímero y captura su salida
#    (script propiedad de esta US: scripts/captura-cancelacion.sh)
bash scripts/captura-cancelacion.sh
```

El script hace exactamente esto, y nada más:

```bash
poetry -P backend run uvicorn app.main:create_app --factory --port 8123 \
  > docs/evidencia/us-023/servidor.log 2>&1 &
SERVIDOR=$!
sleep 2
# curl aborta a los 0.4 s: el socket se cierra a mitad de stream
curl -sN -X POST http://127.0.0.1:8123/api/chat \
  -H "Authorization: Bearer ${TOKEN_DEMO}" -H "Content-Type: application/json" \
  -d '{"conversacion":"morosidad","mensaje":"..."}' --max-time 0.4 || true
sleep 1
kill $SERVIDOR
grep '"event": "chat.stream.cancelado"' docs/evidencia/us-023/servidor.log \
  | tee docs/evidencia/us-023/cancelacion.log
```

**Campo que la hace inequívoca**: el nombre del evento `chat.stream.cancelado`. Es inequívoco porque el
generador tiene **dos** salidas mutuamente excluyentes —`chat.stream.completado` y `chat.stream.cancelado`— y la
segunda solo se escribe en la rama de desconexión. Acompañan `stream_id` (correlaciona con el `done`),
`tokens_emitidos` (**mayor que 0 y menor que el total del guion**: si fuera igual al total, el servidor terminó
y el corte fue cosmético) y `duracion_ms`. La línea de evidencia útil es aquella en la que
`tokens_emitidos < tokens_totales_del_guion`; el propio `docs/manual-test/us-023.md` lo dice y pega la salida real.

**Dónde vive la evidencia para A4**: `docs/evidencia/us-023/cancelacion.log` (línea JSON cruda) y
`docs/manual-test/us-023.md` (procedimiento + salida pegada + lectura en prosa de por qué esa línea prueba la
cancelación). De ahí la toma el entregable A4 sin volver a ejecutar nada.

## 2. Arquitectura y flujo de capas

```
NAVEGADOR                          NITRO (Nuxt server)          BACKEND (FastAPI)
---------                          --------------------          -----------------
asistente.vue
  |  enviar()                      frontend/server/api/[...].ts
  v                                   |  reenvia el cuerpo
useChatStream.ts                      |  SIN acumular (stream)
  |  fetch(POST /api/chat,            v
  |        signal: ctrl.signal) --> proxy --> api/chat.py  (router delgado)
  |                                              | Security(get_current_user,
  |                                              |          scopes=["operativo"])
  |                                              v
  |                                    services/chat_stream.py
  |                                       | registra stream_id en _STREAMS_ACTIVOS
  |                                       | async for evento in proveedor.generar(peticion)
  |                                       |     if await esta_desconectado(): -> cancelar
  |                                       v
  |                                    services/proveedores/  (Protocol ProveedorDeTokens)
  |                                       +-- guionizado.py   (S4: guion determinista)
  |                                       +-- [gemini.py]     (solo si go/no-go = GO)
  |  <-- event: tool_call\ndata: {...}\n\n
  |  <-- event: token\ndata: {...}\n\n
  |  <-- event: done\ndata: {...}\n\n
  v
lector.read() -> parser de framing -> onEvento(tipo, datos)
  |
  +--> tarjetas.set(id, ...)  -> ToolCallCard (US-028, aun no existe: fallback textual)
  +--> texto += token.texto
  +--> error                  -> AvisoError (US-024, aun no existe: fallback textual)
```

**Recorrido petición → respuesta, paso a paso**

1. `asistente.vue` llama `enviar(mensaje)` del composable. El composable crea un `AbortController` nuevo y pasa
   a estado `generando`; el botón Detener aparece **en ese instante**, antes de que llegue el primer byte.
2. `fetch('/api/chat', {method:'POST', signal})`. La cookie de sesión viaja sola; el proxy Nitro la traduce a
   `Authorization: Bearer`.
3. El router `POST /api/chat` resuelve `Security(get_current_user, scopes=["operativo"])`. Si falla, **no hay
   stream**: es un 401/403 JSON normal, porque un error de autorización antes de abrir el stream no puede
   viajar como evento SSE (el cliente aún no tiene parser montado). Esto es distinto de un 403 **a mitad** de
   stream, que sí es `event: error` con `clase: "permiso"` y es propiedad de US-024.
4. El router construye la `PeticionChat`, obtiene el proveedor de `Settings.chat_provider` y devuelve
   `StreamingResponse(chat_stream.transmitir(...), media_type="text/event-stream", headers=...)`. **Cero lógica
   en el router.**
5. `chat_stream.transmitir` da de alta el `stream_id`, itera el proveedor, serializa cada evento al framing SSE
   y comprueba la desconexión **en cada vuelta**.
6. Al terminar —normal, cancelado o con error— el `finally` da de baja el `stream_id`, emite el log de cierre y
   cierra el proveedor con `aclose()`.
