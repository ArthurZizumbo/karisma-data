# Pruebas manuales — US-018 / US-019 (Administración de usuarios)

**SHA base**: `a251652` · **Rama**: `us-018` · **Fecha**: 13-ago-2026

Aquí está solo lo que la suite **no** puede demostrar. Las 65 pruebas de `tests/backend/usuarios/`
sustituyen `get_admin_user_repository` con un doble en memoria, porque la suite de este proyecto
corre **sin PostgreSQL** por una decisión que US-002 estableció y que US-015 y US-016 conservaron.
Esa decisión deja una capa fuera del alcance automático: **`SqlAdminUserRepository` es el único
módulo del proyecto que escribe `app_user`**, y ninguna prueba lo ejecuta contra un motor real.
La §6.3 del plan declaró esa brecha en vez de disimularla; **este documento es lo que la cierra**.

> **Estado de ejecución: EJECUTADO el 13-ago-2026** por el orquestador, con `karisma-data-db-1`
> (`pgvector/pgvector:pg15`) en Docker publicando el `127.0.0.1:55432`, y el backend de esta rama
> servido en el `8001` contra esa base. Toda la salida de abajo está pegada tal como salió.

## Por qué el backend se levantó a mano y no con `make dev`

El contenedor `karisma-data-api-1` llevaba seis horas arriba y **es anterior a esta US**: su
`openapi.json` devolvía `[]` al buscar rutas de usuarios. Reconstruirlo habría reiniciado la API que
estaban usando las sesiones paralelas de US-009 y US-023, así que se sirvió esta rama en un puerto
aparte contra la **misma** base.

Al hacerlo apareció una fricción del entorno que conviene dejar escrita, porque **le va a pasar a
cualquiera que sirva este backend desde Windows y no desde el contenedor**:

```
sqlalchemy.exc.InterfaceError: (psycopg.InterfaceError) Psycopg cannot use the
'ProactorEventLoop' to run in async mode.
```

En Windows, `asyncio` usa `ProactorEventLoop` por omisión y `psycopg` no funciona en modo async
sobre ese bucle; dentro del contenedor Linux no ocurre. **No es un defecto de esta US ni del
proyecto**: es la razón de que el entorno canónico sea Docker. Fijar la política de bucle antes de
`uvicorn.run` **no basta**, porque uvicorn monta el suyo; hay que construir el `Server` con
`loop="none"` y servirlo dentro de un `asyncio.run` que ya corra sobre el bucle *selector*.

### 1.5 Cambio de rol: la marca de tiempo la pone la base — B-6

```
antes  : analista  2026-08-11T21:15:02.066730Z
despues: operativo 2026-08-14T00:01:08.418520Z
```

Esto es lo que ninguna prueba automática de esta US puede demostrar: el doble en memoria estampa la
fila **él mismo**, así que mide que el servicio pide la escritura, no que el `now()` del motor la
fecha. Aquí la fecha la puso PostgreSQL.

### 1.6 Borrado lógico e idempotencia — CA-4 y B-12

```
DELETE /api/users/{jmendieta}   ->  disabled: True | updated_at: 2026-08-14T00:01:08.583863Z
total tras el DELETE: 7 | jmendieta sigue en la lista: True

DELETE /api/users/{jmendieta}   ->  disabled: True | updated_at: 2026-08-14T00:01:08.583863Z
```

Dos cosas, y la segunda es la que importa. **El usuario sigue en el listado y `total` no baja**: la
desactivación es lógica y la auditoría que `db/AGENTS.md` exige preservar se preserva. Y el segundo
`DELETE` devuelve **la misma marca de tiempo, al microsegundo**: la idempotencia no es «responder
200 dos veces», es **no escribir cuando la fila ya está en el estado pedido**. Sobre el motor real
se ve que no hubo segunda escritura.

Reactivación por el camino que la ambigüedad 3 eligió, `PATCH` y no un endpoint nuevo:

```
PATCH {"disabled": false}  ->  disabled: False
```

## 2. El ciclo de la migración — CA-15

**Se corrió sobre una base desechable, `karisma_reversibilidad`, y no sobre `karisma`.** El motivo es
concreto: un `rollback` sobre la base compartida le habría quitado la columna en caliente a dos
sesiones que estaban trabajando.

```
1. dbmate up  (aplica las seis migraciones)
   Applying: 20260811005732_enable_pgvector_extension.sql
   Applying: 20260811211250_create_app_user.sql
   Applying: 20260812065546_create_catalog.sql
   Applying: 20260812121501_create_catalog_lineage.sql
   Applying: 20260813204211_create_export_job.sql
   Applying: 20260813205114_add_app_user_updated_at.sql      <- la de esta US
   updated_at presente : 1
   ultima version      : 20260813205114

2. dbmate rollback
   Rolling back: 20260813205114_add_app_user_updated_at.sql
   updated_at presente : 0
   ultima version      : 20260813204211                      <- cae a la de US-009

3. dbmate up
   Applying: 20260813205114_add_app_user_updated_at.sql
   updated_at presente : 1
   ultima version      : 20260813205114

4. filas sembradas con updated_at = created_at:  7 de 7
```

`db/schema.sql` se resguardó antes del ciclo y se restauró después; quedó **byte a byte idéntico**, y
la base desechable se eliminó.

> **Este ciclo demuestra, de paso, la trampa que el handoff anota para quien siga.** La migración de
> esta US (`20260813205114`) quedó **por encima** de la de US-009 (`20260813204211`), así que
> `dbmate rollback` revierte **la de US-018**, no la de quien lo lance. Se ve en el paso 2: la última
> versión cae a `20260813204211`. Cualquiera que pruebe reversibilidad desde otra US sobre la base
> compartida le quitará la columna a `app_user` sin pretenderlo.

## 3. Lo que sigue pendiente, y por qué

**El diálogo en navegador real.** `happy-dom@20.11.2` implementa `showModal()` como
`setAttribute('open','')` (`lib/nodes/html-dialog-element/HTMLDialogElement.js:81`): no atrapa el
foco, no reacciona a `Esc` y no emite `cancel`. Por eso `dialogoConfirmacion.spec.ts` prueba **los
tres manejadores propios** del componente y deja al navegador lo que solo el navegador tiene:

| Comprobación | Estado |
|---|---|
| `Esc` cierra el diálogo sin ejecutar la acción | **pendiente** |
| El foco no sale del diálogo con `Tab` | **pendiente** |
| Al cerrar, el foco vuelve al botón que lo abrió | **pendiente** |
| El clic en el telón cierra | cubierto en vitest por el manejador propio; falta confirmarlo con la capa superior real |
| El fondo queda inerte | **pendiente** |

No se ejecutaron porque exigen el frontend servido contra este backend, y **el puerto 3000 estaba
ocupado** por una de las sesiones paralelas. Levantar un segundo Nuxt habría competido por CPU con
trabajo del usuario en curso. Es una comprobación de una sola pasada: se hace junto con la captura
del prototipo 5 para A4.

**El efecto en la siguiente petición** (degradar a un analista con sesión abierta y ver su 403; un
usuario desactivado recibiendo 401 `sesion_revocada`) también queda para esa misma pasada, por el
mismo motivo. La mecánica que lo produce no es de esta US: es `get_current_user` de US-015
recargando la fila en cada petición, y su suite ya la cubre.
